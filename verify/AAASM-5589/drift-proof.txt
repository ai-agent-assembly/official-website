Every MEASURED field reproduces exactly. One field is excluded and does not:
`provenance.capturedOn` advances to the day the re-record actually ran,
because the measurement was genuinely re-taken. (It reads `unchanged` above
only because the re-run happened on the same day as the original.)

That exclusion is stated rather than hidden, and it is narrow by
construction: `scripts/denied-action-capture.py` takes the date from the
clock inside the run and offers NO WAY to override it, so the field cannot
be made to disagree with the run it labels. An earlier version of this
script had a `--date` argument, which meant someone could re-measure today
and stamp last week -- a hand-settable timestamp on a page whose whole
argument is that a stated fact was checked. It was removed.

  THE EXCLUSION IS NOT A HOLE -- FOUR CONTROLS
  --------------------------------------------
  A field nothing compares is a field anything can be, so the excluded one
  is asserted separately and the comparison is shown failing.

  A  baseline differing ONLY in capturedOn (2026-08-07 vs 2026-08-14)
       -> "excluded : provenance.capturedOn 2026-08-07 -> 2026-08-14 (advanced)"
       -> PASS, EXIT=0        the exclusion works
  B  baseline with arms[0].observedSideEffect flipped true
       -> "FAIL: the re-record differs from the baseline in a measured field."
       -> EXIT=1              the comparison can still fail
  C  capturedOn set to 2099-01-01
       -> "FAIL: provenance.capturedOn is in the future: 2099-01-01 > 2026-08-14"
       -> EXIT=2              a future date is refused
  D  capturedOn set to 'last tuesday'
       -> "FAIL: provenance.capturedOn is not an ISO date: 'last tuesday'"
       -> EXIT=2              a malformed date is refused

  B is the one that matters: without it, "everything else matched" would be
  a claim about a comparison nobody had shown capable of disagreeing.

5. WHAT THE RECORDED RUN DOES AND DOES NOT ESTABLISH
================================================================
Establishes, for this run only:
  - The tool body did not take effect. Read from a directory listing taken
    by a separate OS process importing only `os`, `sys` and `json`.
  - The refusal preceded the effect. The same tool, same policy, with the
    shim removed, wrote the file (section 1 and the `enforcement_removed`

    file (`allowed` row). Both controls came out the other way.

    would reach only `Evaluated`; the post-condition is what carries it.

Does not establish, and the page says so:
  - Anything about a second tool, a second framework, a second SDK, a second
    platform, or the other language SDKs.
  - Anything about a gateway producing the verdict. The decision came from
    an in-process interceptor in the SDK's `enforce` posture.
  - Anything about durable audit evidence. Neither audit hook resolves on
    the SDK's own shipped interceptor, so a denied call leaves nothing
    behind; SDK-side recording is `Planned` under §6.
  - Anything about a tool body reached by a route other than the framework's
    tool-execution entry.
